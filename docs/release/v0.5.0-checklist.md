# ASC v0.5.0 — 릴리스 체크리스트 (조율 capability + 상시 runtime P0)

정본 경로는 2단계다: `.github/workflows/release.yml` (Stage 1 — publish) 이후
`.github/workflows/release-finalize.yml` (Stage 2 — provenance 기반 tag·Release).
이 문서는 수동 fallback 절차와, 워크플로가 대신할 수 없는 인수 확인의 기록이다.

## 이 릴리스가 싣는 것

0.4.0 이후 main 의 PR #28~#39.

- **조율 증거 (#30·#31·#32·#33·#35)** — 물었다·닿았다·답이 왔다를 세 사실로 가른다.
  찾기 → 판정 → 만들기 → 되읽기, 신원은 주소가 아니라 안정 id, 공개 payload 는 타입.
  GitLab 이 첫 실제 표면. `asc coordination publish / observe`.
- **정본 읽기 (#34)** — profile 이 `git` 이라 선언한 갈래는 checkout 에서 읽는다.
- **상시 runtime P0 (#36·#37·#38)** — 서비스 문맥 PATH, 회차 종료 코드 집계, 커서 단조성.
- **hygiene (#39)**, 릴리스 인프라 (#28·#29).

minor bump 근거: `coordination.surface` capability 와 `asc coordination` 명령이 공개 표면에
추가됐다. 중복 REQ 는 결함이 아니었으므로 수정으로 쓰지 않는다.

## Gate (publish 전 — 워크플로가 재실행하는 것과 동일)

```text
[ ] npm run typecheck / build / test
[ ] npm run release:check
[ ] npm run pack:all && npm run smoke    (이 기계의 smoke 15건 실패는 전역 설치 존재 때문 — 0.4.0 과 동일, CI 에서 판정)
[ ] npm run presentation:check
```

## 수동 fallback (워크플로 불능 시에만)

```text
[ ] publish @asc-agent/runtime   → verify on the registry
[ ] publish @asc-agent/bootstrap → verify   (bootstrap 이 runtime 을 exact 로 가리킨다 — 순서 고정)
[ ] published smoke → 인수 → finalize (tag·Release 는 Stage 2 가 만든다)
```

## Published acceptance (게시본으로만 — source checkout 금지)

```text
[ ] 빈 prefix 에 npm install -g @asc-agent/runtime@0.5.0 (bounded retry 로 전파 대기)
[ ] which asc 가 그 prefix 를 가리킨다 — ~/projects/asc 나 dev dist 면 실패
[ ] asc --version → 0.5.0
[ ] asc setup --help · setup status · runtime --help · coordination --help 가 답한다
[ ] npx --yes @asc-agent/bootstrap@0.5.0 setup plan --json (격리 HOME) 이 JSON 으로 답한다
```

## Stage 2 전 확인

```text
[ ] 위 published acceptance 전부 PASS
[ ] tag v0.5.0 미존재
[ ] docs/releases/v0.5.0.md 가 게시된 commit 에 존재
```
