# ASC v0.8.1 — 릴리스 체크리스트 (patch · Windows 상시 등록 수정)

정본 경로는 2단계다: `release.yml` (publish) 이후 `release-finalize.yml` (tag·Release).

## 이 릴리스가 싣는 것

capability 를 늘리지 않는다. 0.8.0 이 Windows 실기계에서 남긴 결함 넷을 고친다.
0.8.0 note 의 마지막 줄이 그 원인을 이미 이름 댔다 — "Windows and Linux lifecycle
commands are exercised in CI, not on a real machine."

```text
D4  execText 가 resolveCommand 를 안 거쳐 Windows 에서 npm 조회가 늘 실패    상류
D1  그 빈 답 뒤에서 sentinel 문자열이 안정 경로로 승격돼 등록물에 박힌다
D2  taskRunLine 이 따옴표를 손으로 이스케이프해 Command 가 공백에서 잘린다
D3  convergeService 가 STALE 을 ABSENT 로 보고하고 수렴 경로가 도달 불가
```

surface 변경 없음 · state schema 변경 없음 · macOS/Linux 등록 경로 무변경.

## Gate (publish 전)

```text
[ ] npm run typecheck / build / test
[ ] npm run release:check          — 0.8.1 명명·note 섹션·버전 리터럴
[ ] npm run pack:all && npm run smoke
[ ] npm run presentation:check
[ ] 3-OS CI green on main          — 병합 커밋 1799fd8 기준
```

## 수동 fallback (워크플로 불능 시에만)

```text
[ ] publish @asc-agent/runtime   → verify on the registry
[ ] publish @asc-agent/bootstrap → verify   (bootstrap 이 runtime 을 exact 로 가리킨다 — 순서 고정)
[ ] published smoke → 인수 → finalize
```

## Published acceptance (게시본으로만 · 새 physical session 에서)

0.8.0 의 Gate A~M 은 이 patch 가 건드리지 않은 축이라 되풀이하지 않는다. 이번 회차가
확인해야 하는 것은 **고친 넷이 게시본에서 실제로 안 나온다**는 것이고, 그 확인은
Windows 실기계에서만 뜻이 있다.

```text
[x] W-1  전역 runtime 이 없는 상태에서 등록 시도                        PASS
         등록 0건 · "service runtime unavailable — no installed ASC runtime
         to point at" · exit 1 · schtasks 항목 0개
[x] W-2  전역 runtime 이 없는 상태에서 setup apply                      PASS
         "status": "applied" · "remaining": []
         0.8.0 이 verification_failed 를 낸 것과 같은 출발 조건
         (runtime=NOT_INSTALLED · persistent=install) 에서 측정했다
[x] W-3  등록된 schtasks XML 실측                                       PASS
         <Command>"C:\Program Files\nodejs\node.exe"</Command>
         절단 0 · 리터럴 \" 0
[x] W-4  runtime service status                                         PASS
         uninstall → "not registered yet" → install → CURRENT
[x] W-5  낡은 명령을 심은 뒤 asc refresh                                PASS
         status 가 STALE 로 읽고 refresh 가 "service: converged with schtasks"
[ ] W-6  asc update (0.8.0 → 0.8.1)                                     FAIL
         0.8.0 의 asc update 가 레지스트리를 못 읽는다:
           {"state":"UNKNOWN","from":"0.8.0",
            "detail":"the registry could not be asked"}
         같은 명령이 0.8.1 에서는 {"state":"CURRENT","from":"0.8.1"} 로 답한다
```

## W-6 판정의 성격 — 게시본 결함이 아니다

`asc update` 는 `npm view` 로 레지스트리를 묻고, 그 호출이 D4 로 죽는다. **0.8.0 은
자기가 가진 결함 때문에 그 결함을 고치는 버전으로 스스로 올라갈 수 없다.** 0.8.1
아티팩트에는 이 문제가 없다 — 결함은 이미 게시된 0.8.0 쪽에 있고, 레지스트리는
immutable 이라 그것을 고칠 방법이 없다.

실제로 동작하는 업그레이드 경로는 이것이고, 이 인수도 그 경로로 올라와서 했다.

```bash
npx --yes @asc-agent/bootstrap@0.8.1 setup apply --json
```

따라서 W-6 의 FAIL 은 **릴리스 노트의 Install / Upgrade 안내가 Windows 의 0.8.0
사용자에게 틀렸다**는 뜻이다. `asc update` 가 첫 줄에 있는데 그 명령이 그들에게는
작동하지 않는다.

게시된 commit 의 노트가 Release body 의 정본이라 이후에 바꿀 수 없다. 이 회차는
tag·Release 를 진행하고 **GitHub Release 본문에 그 안내를 보강**하는 쪽을 택했다 —
0.8.1 의 코드는 W-1~W-5 로 검증됐고, 코드가 같은 0.8.2 를 문서만으로 소비하지 않는다.

## 인수 환경

```text
기계     Windows 11 · Node 24.18.0
출발     전역 @asc-agent/runtime 0.8.0 · 등록 있음
경로     npm uninstall -g → npx bootstrap@0.8.1 setup apply → 0.8.1
복구     인수 후 0.8.1 · INSTALLED_CURRENT · guard READY · AUTO READY ·
         persistent registration 정상 (XML 온전)
```

macOS 는 실기계 등록을 이번에 밟지 못했다 — note 의 Known limitations 에 그대로 적었다.
Mac 이 확보되면 `runtime service install` 1회로 W-3·W-4 에 해당하는 launchd 확인을 한다.
