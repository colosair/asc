# ASC 0.8.1 / JAM 1.6.0 — dogfood 1회차 (Windows)

게시본으로만 측정했다. 개발 checkout 을 경로에 끼우지 않았다.

```text
기계    Windows 11 · Node 24.18.0
ASC     @asc-agent/runtime 0.8.1 (npm 전역) · host 통합 INSTALLED_CURRENT
JAM     @jam-mcp/launcher 1.6.0
날짜    2026-09-07
```

## 측정한 것

```text
[x] Gate A  asc status · jam status 가 답한다                              PASS
[x] Gate B  MANUAL 에서 raw 읽기 통과 · Guard hard-block 0                 PASS
[ ] Gate C  control-plane 이 막힌 fixture 에서 mode auto 가 거부            보류
[x] Gate D  전 축 READY 인 자리에서 mode auto 가 선다                      PASS
[x] Gate E  같은 결정이 MANUAL 과 AUTO 에서 똑같이 올라온다                PASS
[ ] Gate F  work publish 로 GitLab 완주                                    보류
[ ] Gate G  work finish 한 명령으로 handoff·release·collect·archive        FAIL
[~] Gate H  host 설치물 stale → refresh 복구                               부분
[~] Gate I  update → 새 build 가 refresh → INSTALLED_CURRENT               부분
[~] Gate J  격리 환경 uninstall                                            부분

[ ] Gate L  AUTO 에서 같은 작업을 work publish 로                          보류
[ ] Gate M  프로젝트 플러그인 스킬과 1회전                                 보류
```

## PASS 의 근거

**Gate A** — `asc status` 가 설치·모드·세션·대기를 한 화면으로 답한다. `jam status` 는
9개 체크 전부 OK (Node·project config·Jira 키·자격증명·base URL·MCP 기동 5 tools·
인증·JQL 접근·이슈 상세).

**Gate B** — MANUAL 에서 raw 읽기 세 종류가 통과한다.

```text
git fetch --dry-run    rc=0
gh api repos/…         응답 정상
glab issue list        응답 정상
```

`gh api` 는 guard 의 FORBIDDEN 목록에 있는데도 통과했다 — MANUAL 이 강제하지 않기
때문이고, 그것이 이 Gate 가 보려는 것이다. 생성된 hook 을 실제 프로세스로 돌려
판정을 직접 읽었다.

```text
입력   {"tool_name":"Bash","tool_input":{"command":"git push origin main"}}
출력   [ASC] MANUAL — 'git push' 를 막지 않는다. 이 쓰기는 ASC 가 관리하는 경로
       밖으로 나간다.  (+ work publish --review / mode auto 안내 2줄)
exit   0
```

**Gate D** — `asc mode auto` 가 세 축을 물어보고 선다 (executor·guard·control-plane
전부 READY, `applied: true`). 같은 hook 에 같은 입력을 다시 넣으면 판정이 뒤집힌다.

```text
출력   [ASC guard] 이 workspace 는 AUTO 로 관리한다. 'git push' 는 논리 세션 밖에서
       나갈 수 없다.  (+ work start / bind 안내, mode manual 출구)
exit   2
```

한 hook 이 mode 하나로 갈린다 — 두 벌의 규칙이 아니다.

**Gate E** — AUTO 와 MANUAL 에서 `asc inbox` 를 각각 읽었다. 대기 건수 7 로 같고,
목록의 순서와 REQ id 도 같다. 모드는 누가 실행하는지를 정하지 사람이 무엇을
결정해야 하는지를 바꾸지 않는다 — 그 문장이 실제로 지켜진다.

**Gate G** — 부분만 통과했다. 아래 "Gate G — 한 명령이 하나를 빠뜨린다" 참조.

## 보류의 사유 — 못 한 것을 했다고 적지 않는다

**Gate C** — control-plane 을 막으려면 `~/.claude/settings.json` 의 `Bash(asc:*)`
허용 규칙을 떼어내야 한다. 그건 이 세션 자신의 실행 권한을 바꾸는 일이라, 되돌리기
실패가 곧 세션 불능으로 이어진다. 격리된 host fixture 없이 할 일이 아니라고 보고
미뤘다.

**Gate F · K · L · M** — 전부 바인딩된 프로젝트 저장소에 실제 쓰기(part branch push,
MR 생성, 프로젝트 플러그인 스킬 1회전)를 요구한다. 이 세션은 ASC/JAM 제품 관제
세션이고 그 프로젝트의 작업 세션이 아니다. 그 저장소에는 지금 다른 세션들이 커밋
중이라, 여기서 push 를 만드는 것은 남의 작업 위에 끼어드는 일이다.

**Gate H · I · J** — 다른 세션의 `packages/runtime/**` 작업이 리뷰 대기로 넘어간 뒤
착수했고, 각각 절반씩 닿았다. 아래 절에 적었다.

## Gate H·I·J — 절반씩 닿았다

**Gate H** — 설치된 hook 을 일부러 훼손하고 `refresh` 로만 복구되는지 봤다. 복구되지
않았고, **그것이 옳다.**

```text
훼손 후        Installation: INSTALLED_MODIFIED · DEGRADED guard
refresh        "you edited some installed files — leave them, or overwrite with
                install --force"   [modified] …/guard-hook.mjs
복구           asc host claude install --force → INSTALLED_CURRENT (원본 해시 일치)
```

내가 만든 것은 STALE 이 아니라 MODIFIED 였다. ASC 는 둘을 가르고, 사람이 손댄 파일을
`refresh` 가 말없이 덮지 않는다. Gate 가 요구한 STALE 은 이 기계에서 인위적으로 만들 수
없다 — 설치 파일이 manifest 와는 일치하면서 소스와만 다른 상태는 새 버전이 나와야 생긴다.

그 경로는 이번 회차 이전에 이미 측정됐다. 0.8.0 → 0.8.1 로 올라오면서 host 통합이
자연스럽게 STALE 이 됐고, `asc refresh` 한 명령이 `setup` 을 부르지 않고 수렴시켰다
("The installation is behind the current source — converging it" → INSTALLED_CURRENT).
Gate H 가 보려던 것은 그때 충족됐고, 이번에 새로 나온 것은 MODIFIED 쪽 동작이다.

**Gate I** — 다음 후보가 없다. 전역도 레지스트리 최신도 0.8.1 이라 `update check` 가
`{"state":"CURRENT","from":"0.8.1","to":"0.8.1"}` 로 답한다. 정확한 답이지만 "새 build 가
자기 refresh 를 돈다" 는 다음 릴리스에서만 측정된다.

반대 방향은 인수(W-6)에서 측정됐다 — **0.8.0 에서는 `asc update` 로 0.8.1 에 갈 수
없다.** `npm view` 호출이 그 버전에서 죽는다.

**Gate J** — 실제 uninstall 은 하지 않았다. 이 기계 하나뿐이고 격리 환경이 없다.
`uninstall plan` 은 읽기 전용이라 돌렸고, 답이 정확하다.

```json
"remove":   {"service":"schtasks","hostIntegration":true,"runtime":"0.8.1"}
"preserve": {"state":"…/.asc",
             "note":"profiles, workspaces, sessions, audit, evidence and identities all stay"}
"blockedBy":{"sessions":[3건],"bindings":[6건]}
```

살아 있는 세션과 결합이 있으면 거부한다 — 잃을 것을 이름 대고 멈춘다.

## 이 회차에서 새로 관측된 것

**논리 세션을 닫지 못하는 경우가 있다.** `S-20260907-03`(0.8.1 릴리스)이 PAUSED 에서
움직이지 않는다.

```text
The canonical source differs from when this was issued — the ground under the contract moved:
  develop: a351b5ff → 46c2f3b4
Review the changes, and hand the contract back to the Controller if they affect it.
```

정본이 바인딩된 프로젝트의 통합 브랜치인데 그것이 움직여서 resume 이 막힌다. 그런데
그 계약의 산출물은 이 저장소의 릴리스라 그 브랜치와 파일 하나 공유하지 않는다.
`acceptance` 클래스 decision 으로 무관함을 기록해도 상태는 PAUSED 그대로다.

정본 이동을 감지하는 것 자체는 옳다 — 결정이 선 땅이 움직였는지는 물어야 한다.
문제는 **workspace 바인딩과 다른 저장소에서 일하는 계약에는 그 질문이 맞지 않는데
빠져나갈 길이 없다**는 것이다.

**schtasks 등록이 콘솔 창을 띄운다.** 등록된 작업의 `<Settings>` 에
`<Hidden>true</Hidden>` 이 없어 5분마다 콘솔이 깜빡인다. 0.8.1 에도 남아 있다 —
이 릴리스가 잡지 못했다. 다른 세션이 맡았다.

**schtasks 가 간격 변화를 STALE 로 보지 못한다.** 이슈 #62 로 등록했다.

## Gate G — 한 명령이 하나를 빠뜨린다

이 문서를 쓴 세션(`S-20260907-06`)을 `asc work finish` 로 닫아 측정했다. 네 가지 중
셋은 되고 하나는 안 된다.

```text
handoff   OK   "S-20260907-06 DONE — handoff written"
collect   OK   활성 세션 목록과 쓰기 범위 점유가 그 자리에서 갱신된다
archive   OK   audit-del / audit-rec / audit-exec 가 남는다
release   NO   physical binding 이 그대로 남는다
```

0.8.0 릴리스 노트는 이렇게 적었다 — *"`asc work finish` writes the handoff, releases
the physical binding, collects and archives in one command."* 세 번째가 일어나지 않는다.

DONE 직후 같은 Run 으로 다른 세션을 잡으려 하면 거부된다.

```text
RUNTIME_CONFLICT: 이 Run(windows-control-center) 은 지금 S-20260907-06 을 잡고 있다.
한 Run 은 한 세션만 잡는다 — 먼저 놓아라:
  asc host claude release S-20260907-06 --physical windows-control-center
```

상태 파일에도 그대로 남아 있다.

```json
runtime-binding-S-20260907-06.json
{"logicalSessionId":"S-20260907-06","provider":"claude-code",
 "physicalSessionId":"windows-control-center","updatedAt":"2026-09-07T06:02:41.371Z"}
```

`updatedAt` 이 bind 시각 그대로다 — finish 가 이 레코드를 건드리지 않았다.

**끝난 세션이 물리 Run 을 계속 점유한다.** 손으로 `asc host claude release` 를 치기
전까지 그 Run 은 다음 일을 시작할 수 없고, `work finish` 는 그 사실을 말하지 않는다.
"한 명령으로 끝난다" 는 약속이 네 번 중 세 번만 지켜지는 셈이다.

같은 실패를 이 회차에서 세 번 밟았다 — `S-20260907-02`, `-03`, `-04` 를 닫을 때마다
다음 세션 bind 가 `RUNTIME_CONFLICT` 로 막혔고, 매번 손으로 놓았다. 그때는 절차를
잘못 안 줄 알았는데, 측정해 보니 명령이 하는 일이 문서와 다른 것이었다.

이슈 #63 으로 등록했다.

**그리고 이건 오늘 생긴 것이 아니다.** Gate J 의 `uninstall plan` 이 드러냈다 —
`blockedBy.bindings` 에 8월 31일 세션 여섯이 그대로 서 있다.

```json
runtime-binding-S-20260831-01.json
{"logicalSessionId":"S-20260831-01","physicalSessionId":"claude-main",
 "updatedAt":"2026-08-31T08:45:35.237Z"}
```

`-01` 부터 `-05`, 그리고 `-30`. 일주일 전 세션들이 물리 Run `claude-main` 을 아직 쥐고
있고, 그 때문에 **이 기계는 uninstall 도 할 수 없다.**

한 세션이 놓지 않은 것은 다음 bind 에서 걸린다. 여섯이 쌓인 것은 아무 데도 안 나타난다 —
`asc status` 도 `session list` 도 말하지 않고, uninstall 을 계획할 때 한꺼번에 드러났다.
