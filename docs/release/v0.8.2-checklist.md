# ASC v0.8.2 — 릴리스 체크리스트 (patch · Windows 실행 경로와 결합 해제)

정본 경로는 2단계다: `release.yml` (publish) 이후 `release-finalize.yml` (tag·Release).

## 이 릴리스가 싣는 것

capability 를 늘리지 않는다. 두 갈래를 고친다.

```text
#65  runExternal 하나로 shim 해석 + windowsHide 통합
     JAM doctor·probe·heal 이 serve 와 같은 해석을 쓴다 (Windows 에서 spawn ENOENT 였다)
     자식 프로세스의 콘솔 창이 사라진다
     schtasks status 가 /Query /XML 로 간격까지 비교한다 (#62)
#66  work finish 가 physical binding 을 놓는다
     terminal 세션이 Run 을 쥔 것을 status 가 이름과 명령으로 드러낸다 (#63)
```

surface 변경 없음 · state schema 변경 없음 · `~/.asc` 무변경.

## 측정

**X-1** — 인수용 세션 `S-20260907-08` 을 만들어 bind 하고 `asc work finish` 로 닫았다.

```text
finish 전   runtime-binding-S-20260907-08.json  존재
finish 후   No such file or directory
다음 bind   S-20260907-01 ← windows-control-center (owner claim)
            RUNTIME_CONFLICT 없음
```

0.8.1 에서는 이 자리에서 막혔고, 그것을 오늘 세 번 밟았다.

**X-2** — 게시본 0.8.2 의 `asc status` 가 Degraded 절에서 이름을 댄다.

```text
- 6 finished session(s) still hold a Run — S-20260831-01, S-20260831-02,
  S-20260831-03, … (asc host claude release <S-ID> --physical <run>)
```

같은 순간 0.8.1 은 `- this machine has no persistent registration` 한 줄뿐이었다.

**X-3** — 이 회차의 핵심 항목. **수정이 무엇을 하지 않는가**를 잰다.

```text
인수 전   runtime-binding-*.json  8개
인수 후   8개 → X-1 이 만든 것 하나가 빠지고, 8월 31일 여섯은 그대로
살아 있는 세션 둘(S-20260907-01 · -07)은 "finished" 로 세지 않는다
```

드러내되 지우지 않는다는 조건이 실제로 지켜진다. terminal 인 것만 세고, 세면서도 건드리지
않는다.

**X-5** — 5분으로 등록한 뒤 60분으로 재등록하고 기본 기대(5분)로 판정시켰다.

```text
status   registration is behind — com.asc-agent.runtime repeats every PT1H,
         not every 5 min
XML      <Interval>PT1H</Interval>
```

Task Scheduler 가 `/MO 60` 을 `PT1H` 로 정규화한 것을 그대로 읽고 분으로 환산해 비교한다.
`60분 등록 · 60분 기대 → CURRENT` 쪽은 CLI 로는 잴 수 없다 — `service status` 에 기대
간격을 주는 인자가 없다. 그 절반은 어댑터 단위 테스트가 덮는다.

측정 뒤 등록은 **같은 턴 안에 지웠다.** 콘솔 창이 주기적으로 뜨는 상태를 남기지 않는다.

**X-6** — 0.8.1 W-6 의 짝이 성립했다.

```text
asc update
  Update available — 0.8.1 → 0.8.2
  installed: @asc-agent/runtime@0.8.2
  refresh: Install state: INSTALLED_CURRENT
  asc 0.8.2 is current.
```

0.8.0 은 `npm view` 가 죽어 여기 도달하지 못했고, 레지스트리가 immutable 이라 그 버전은
영원히 그 상태다. 0.8.1 부터는 정상 경로로 올라온다 — D4 수정의 실제 값어치가 이것이다.
이 절차가 동시에 릴리스 체크리스트의 "새 build 가 자기 refresh 를 돈다" 도 충족한다.

## X-4 — 측정 불가, 그리고 그 자체가 관측이다

`asc status` 에 jam 이 한 글자도 없다. `--json` 에도 없다.

```text
github      READY  executor 로 뜬다
gitlab      External read: gitlab-todo 로 뜬다
jam         후보에도, unavailable 목록에도, --json 에도 없다
```

이 workspace 의 profile 에 jam binding 선언이 없어서다. 그래서 사용자는 **JAM 이 안 붙은
것인지, 붙었는데 고장인지, 원래 안 쓰는 것인지 구분할 수 없다.** `unavailable` 은 "자격이
없어 못 만들었다" 는 말하지만 "선언이 없어 후보도 아니다" 는 아무 데서도 말하지 않는다.

두 사실을 갈라 적는다.

```text
다른 세션이 잰 것   코드가 고쳐졌다 — 어댑터를 직접 불러 대조
                    게시본 0.8.1: UNAVAILABLE "spawn npx ENOENT"
                    고친 빌드:    AVAILABLE "연결 확인됨"
이 인수가 못 잰 것  그 코드에 닿는 길이 이 구성에 없다
```

둘 다 참이고 서로를 대신하지 않는다. `#65` 가 고친 것이 게시본에서 동작하는지는 jam
binding 이 선언된 workspace 에서 다시 재야 한다.

## X-7 — 사람 눈이 필요하고, 반만 묻는다

콘솔 창은 화면 관측이라 세션이 판정할 수 없다. 두 층을 갈라 물었다.

```text
(a)  runtime tick 회차 동안 창이 깜빡이는가    #65 가 고쳤다고 주장하는 부분
(b)  등록이 있을 때 5분마다 창이 뜨는가        고치지 못한 부분
```

**(b)는 묻지 않았다.** 답이 이미 정해져 있고(뜬다), 확인하려면 등록을 다시 만들어 5분을
기다려야 한다 — 아는 사실을 확인하려고 사용자 화면에 창을 띄우는 일이다. 노트 Known
limitations 에 "고치지 못했다" 로 적혀 있고 그 진술이 이미 정확하다.

**(a) PASS — 사용자 관측.** `asc.cmd runtime tick --all` 이 도는 동안 창이 뜨지 않았다.

한 번 헛짚을 뻔했다. 첫 실행은 이렇게 끝났다.

```json
{"ran": [], "skipped": [], "busy": true}
```

lease 를 다른 호출이 쥐고 있어 **아무 일도 하지 않은 회차**였다. 창이 안 뜬 것이 당연했다 —
부를 자식 프로세스가 없었으니까. 그 상태로 PASS 를 적었으면 아무것도 재지 않은 것을
증거로 삼는 셈이었다.

다시 돌린 회차는 실제로 외부를 쳤다.

```text
[code-primary · gitlab:…] detected 4 · logged 4 · packets 3
실행 delta, reconcile, digest · 간격 대기 census
Machine pass ok — 1 passed
```

`gitlab-todo` 를 조회해 REQ 넷을 새로 만들었다. 자식 프로세스가 실제로 돌았고, 그때도
창이 뜨지 않았다. 이것이 (a)의 근거다.

**코드가 옳다는 것과 화면이 조용하다는 것은 다른 사실이라, 코드 증거로 (a)를 통과시키지
않았다.** 판정의 근거는 사람이 화면을 본 것 하나뿐이다.

**#67(개발 빌드 식별)은 이 회차에서 확인할 수 없다.** 지금 재현되는 이유는 다른 세션의
개발 빌드 소스가 게시본보다 앞서 있기 때문이고, 0.8.2 가 나가면 그 둘이 같아져 STALE 이
나오지 않는다. 다음 수정 커밋이 들어가야 다시 재현된다 — 인수 항목으로 세우지 않는다.

macOS·Linux 실기계 등록은 이번에도 못 밟는다 — Mac 이 없다. 노트 Known limitations 에
**두 릴리스째**로 명시했다.

## 이 회차가 안고 가는 것

```text
예약 작업 자체의 콘솔 창    /RU /NP 는 관리자 권한 필요, Hidden 은 UI 목록 플래그 —
                            둘 다 실측으로 막혔다. wscript 래퍼는 ASC_HOME 에 파일을
                            더하는 설계 결정이라 별건이다
macOS·Linux 실기계          두 릴리스째 미실행
개발 빌드 식별 불가          --version 도 runtime status 도 게시본과 구분되지 않는다.
                            개발 빌드가 대는 Next: asc refresh 를 그대로 치면 미게시
                            코드가 host 통합에 들어간다
```

셋 다 노트 Known limitations 에 적었다. 적었다는 것이 해결했다는 뜻이 아니다.
