ASC 0.10.0 has one subject: the normal path closes without advanced primitives. The
first product dogfood on 0.9.1 (a real work item, from a natural-language request to a
merge request, on a self-hosted GitLab) went through — and on the way a person had to
know four things they should never have needed: `asc session issue`, a `--body-file` for a
`git.push` that carries no body, `asc setup identity --actor local:…` after publish had
already refused, and `--as` on every publish. Status pointed at the inbox through all of
it, the ownership recovery lived under `asc host claude bind --force`, and the work-state
judgement cited the wrong commit. This release closes those seven, in the layer each one
belongs to.

Nothing here adds a provider concept to Core, revives any shell interception, or invents
an authority. The persisted change is one new record kind (contract proposals) and four
optional fields on the delegation record.

## What changed

**Issuing the first contract is one word, or none.** When issuance is the Controller's,
`asc work start <KEY>` now saves the contract it derived as a proposal (`CREATED →
ISSUED | REVISED | REJECTED | OBSOLETE`, kept under the workspace's own `proposals`
scope, not the monitor ledger) and the person issues it with `asc work issue <S-ID>` — or
declines it with `--reject <reason>`. The agent passes what it verified on the same
command (`--criteria`, `--boundary`, `--provenance`), so nothing is retyped and nothing is
lost between "plan" and "issue". A newer proposal for the same work item revises the older
one; a proposal whose work item changed since it was saved is closed `OBSOLETE` at issue
time and the work is re-planned. Setup now asks the person once whether to delegate
issuance (`asc setup delegate --role implementer` or `--none`); with delegation, `work
start` issues and starts on its own, inside the range it proposed and behind the existing
repository-wide backstop. The delegation record separates who issued (`issuedBy`), on
what authority (`controller` or `delegated`, with `delegatedBy`) and which Run wrote it
(`recordedBy`).

**Approvers are mapped to this machine, on purpose.** Publish verifies the approver on
the local channel, and setup used to record only the remote channel name — so status said
approval was open and publish said `FORBIDDEN_ISSUER`. Setup now discovers the local
candidates and stops with `ASC_LOCAL_IDENTITY_REQUIRED` until the person maps one
(`asc setup identity --actor local:<name> --role controller`); no authority is derived
from an OS user name. The approval gate checks the local channel, the refusal names that
command, and `--as` is optional exactly when one approver is mapped here — with several,
naming one is the decision.

**Every managed action declares its payload.** `ports/scm.ts` carries a contract per
action — `required`, `optional` or `forbidden`. `git.push` is forbidden a body: passing
one is refused (exit 2), not warned about and dropped. Actions that publish a person's
text still require it. Core takes `payloadRequired` as an input and still does not know
what an action means.

**One blocker model.** `core/operator/blockers.ts` says what is blocked, why, who resolves
it and a semantic remediation (`RESOLVE_PROFILE_DRIFT`, `MAP_LOCAL_IDENTITY`,
`RECLAIM_SESSION`, …). One CLI table turns those into commands, so `asc status`'s new
`Blocked:` section, its `Next:`, the bootstrap guard and `work start` all name the same
remedy. A `work start` that did not obtain ownership now says so on stdout as well as
stderr.

**Ownership recovery is a work command.** `asc work reclaim <S-ID>` shows the holder,
since when, and the last progress report, then takes the session over and records that a
person did. It is the same rebind `host claude bind --force` performed; the surface moved.
A finished session's leftover binding is released with an audited
`RELEASED(reason=terminal-holder)` — from `reclaim`, and automatically before this Run
claims its next session — instead of being forgotten silently.

**Work-state evidence has to be right, not just the verdict.** Branch refs and
canonical-history mentions now match the work key exactly (`PROJ-64` no longer hits
`PROJ-641`). A branch at the canonical tip with none of this work's commits is reported as
an empty branch and excluded from the merge evidence. A branch checked out in another
worktree with uncommitted changes surfaces as `IN_PROGRESS_ELSEWHERE` — no second
session. A mention whose changed files overlap none of the work item's paths is named as a
possible key collision and leaves the verdict `UNDECIDABLE` (`implementation-evidence`).
When a person overrules a verdict, `asc work start <KEY> --fresh "<reason>"` prints the
overruled evidence again and writes the override to history.

**Handed commands paste.** `shorthandCommand` shell-quotes its arguments; the advanced
`session issue` handout no longer splits its goal into words or turns `>` into a redirect,
and it carries owner, domain and authority like `session plan` does.

## Install / Upgrade

```bash
asc update
```

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.10.0 setup apply --json
```

After upgrading, `asc setup` (or `asc status`) may ask two one-time questions on an
existing workspace: the local approver mapping and the issuance delegation. Both are a
person's; nothing is assumed in their absence.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.10.0 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- **`asc work publish --action git.push … --body-file <path>` exits 2.** The body was never
  read; it is now refused. Actions that publish text still require `--body-file`.
- **`--as` may be omitted** on `work publish` and `grant issue` when exactly one approver
  is mapped to this machine (`local:<name>` in identities.json). With none, publish stops
  and names `asc setup identity`; with several, `--as` is required.
- **`asc setup` on an attached workspace can return `user_action_required`** with
  `ASC_LOCAL_IDENTITY_REQUIRED` or `ASC_ISSUANCE_DELEGATION_DECISION` until the person
  answers. Existing workspaces keep working meanwhile — the defaults are unchanged (no
  delegation; publish refuses without a local approver, as it always did).
- **`asc work start <KEY>` without delegation saves a proposal** and prints `asc work
  issue <S-ID>`. The JSON still carries `forController` for the advanced surface.
- **New commands:** `asc work issue`, `asc work reclaim`, `asc setup delegate`,
  `asc work start --fresh`. Nothing is removed; `session issue` and `host claude bind
  --force` remain as the advanced/recovery surface.
- **Persisted:** contract proposals under the workspace `adapters/proposals/` scope (new);
  `DelegationRecord` gains optional `authority`, `delegatedBy`, `recordedBy`, `proposalId`;
  binding-log `RELEASED` entries may carry `reason`. Session, grant, request and Profile
  schemas are unchanged. Writing `issuanceDelegation` into override.json changes the lock
  digest; `asc setup delegate` re-locks by itself.
- `asc status` JSON gains `blockers`; `degraded` keeps only non-blocking notes.
- `IN_PROGRESS_ELSEWHERE` is a new `WORK_STATE` value; `UNDECIDABLE` can now name
  `implementation-evidence` in `missing`.

## Verified

- Three-OS CI: typecheck, build, the full suite (1727 tests, 1726 pass / 0 fail / 1
  skipped), release checks, packaging, packaged smoke.
- **Payload contract.** Every managed action has one; `git.push` refuses a body before
  review; Core issues an empty-body grant only when told `payloadRequired: false`.
- **Local approver.** Setup returns `ASC_LOCAL_IDENTITY_REQUIRED` with candidates and
  writes nothing; the approval gate is BLOCKED with a remote-only approver; `--as`
  resolves to the single local approver and refuses on zero or several.
- **Blockers.** Ordering, semantic remediations without command strings in Core, the CLI
  table, and the ownership line on stdout.
- **Proposals.** Lifecycle, revision of an older proposal for the same work item, the
  fingerprint check, `work issue` end-to-end through the CLI with the delegation record's
  four new fields, `--reject`.
- **Reclaim.** Another Run's session taken over with evidence and a `SUPERSEDED →
  CLAIMED` log; a finished session's binding released with `reason: terminal-holder`, both
  explicitly and before the next claim.
- **Work state.** Exact key matching on refs and log; empty branches; other worktrees;
  off-target mentions → `UNDECIDABLE`; `--fresh` writes `work_state_overridden` to history.
- **Unchanged invariants, still green:** provider-neutral Core gate; Review → Grant →
  Executor → Verify; one-shot grants; drift refusal; freeze before CLAIM; binding
  CLAIM/CONFLICT semantics; MANUAL/AUTO wording; the 0.9.0 retirement of the guard hook.
- Published acceptance on the maintainer's macOS host against the real product workspace is
  recorded in `docs/release/v0.10.0-checklist.md` under its execution-record section,
  merged to `main` before the tag.

## Known limitations

**Liveness is still not observed.** `work reclaim` shows the holder and the last report; it
cannot say whether that Run is alive. That is the person's call, recorded as one. A
host-side hint was considered and left out of this release.

**Resource identity is still path-only, and a Profile with two bindings for one adapter is
still refused.** Neither was reached by the dogfood; both stay queued behind a real need.

**GitHub has no pre-execution `review()`.** Unchanged; no GitHub publish has been asked for.

**Proposals are not migrated across workspaces and are not archived.** They are small
per-work-item files; a workspace can accumulate closed ones. Nothing reads them after
they close except `work issue`, which reports their status.

**Deprecated aliases (`asc init`, `asc proceed`, `asc progress show`) still answer.** Their
removal was due in this minor by the two-minor policy and is deferred again so this
release stays on its one subject.

**Windows is covered by CI only.** The checklist carries a Windows acceptance line; if it
is not taken, it is recorded as not taken.
