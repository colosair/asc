ASC 0.4.0 removes the step where you start it. Once setup attaches a workspace, one
user-scope runtime on that machine keeps observing it — through terminals closing, hosts
closing, and the runtime process being replaced. Opening a supported host in any checkout
of that project, including a worktree ASC has never seen, restores what is already there.

## What changed

- **Linked worktrees resolve to their workspace.** A checkout created with
  `git worktree add` now resolves to the same logical workspace as its siblings and
  registers itself on the way past. The evidence is local repository structure, not the
  remote URL, so two independent clones of the same remote stay separate — agreement on a
  remote remains a recovery candidate a person confirms.
- **Observation continues without a conversation.** A workspace lease, heartbeat and
  reclaim keep exactly one pass running per workspace, and `asc runtime stop` ends a
  detached one promptly. `asc runtime start --detach` remains for development and
  recovery; it is no longer how the product runs.
- **A machine-level runtime, registered once.** `asc runtime service install` registers a
  single user-scope entry — a LaunchAgent on macOS, a user Scheduled Task on Windows, a
  `systemd --user` timer on Linux — and that one entry covers every workspace the machine
  knows. None of them escalates to root, and none enables lingering on your behalf.
  Registration joins the existing detect → plan → apply → verify path rather than adding
  an activation step of its own, and it happens only from an installed runtime.
- **Workspaces that are not there are left alone.** Operational state is derived from the
  index that already exists: a live checkout makes a workspace active, no live checkout
  makes it dormant. Dormant means no polling and no deletion, and a new checkout brings
  it back.
- **Host sessions restore what is waiting.** A supported host opening in an attached
  directory reports pending decisions, running sessions and monitoring health without a
  command. It reads and never writes: no session is created, no approval consumed. Other
  tools' host hooks are preserved, reinstalling adds no duplicates, and uninstalling
  removes only what ASC owns.
- **A project can watch its code and its work items at once.** Where a profile declares a
  code binding and a work binding, each opens its own observation channel with its own
  cursor and dedupe, and one channel failing no longer silences the other. Previously the
  overlap between them was read as ambiguity and monitoring did not run at all.
- **JAM readiness comes from JAM.** Its own diagnosis is translated by code, never prose,
  into a person's decision, something JAM's official setup can repair, or a state a rerun
  will not change. A profile that already declares a JAM binding is not asked about again.
  Credentials remain JAM's: ASC never receives, stores, or enters one.
- **Machine-wide visibility.** `asc runtime list` answers for every workspace at once, and
  `asc runtime status` reports the registration alongside the build in use.

## Install / Upgrade

```bash
npx --yes @asc-agent/bootstrap@0.4.0 setup apply --json
```

Already installed:

```bash
npm install -g @asc-agent/runtime@0.4.0
```

Existing state is read as it is. Workspaces, profiles, sessions, checkpoints, handoffs,
decisions and audit records are preserved; nothing is migrated or rewritten.

## Agent setup

The canonical entry is unchanged, and there is no new activation step to run after it:

```bash
npx --yes @asc-agent/bootstrap@0.4.0 setup apply --json
```

`setup status --json` still reports `READY`, `UNATTACHED`, `BROKEN` or `LOCK_DRIFT`, and
the plan now also carries the machine registration when one is missing. Do not add a
`runtime start` or `runtime enable` step to any instructions: those surfaces exist for
development and recovery, not for the normal path.

## Compatibility

- Node 24 or newer, unchanged.
- State schema unchanged. No migration runs and none is required.
- No command was removed. `runtime start --detach` and `runtime tick` still behave as
  they did.
- The machine registration is only planned when the running entry is an installed
  package, so running from a checkout changes nothing about the machine.
- JAM is consumed through its published packages at the version JAM reports for itself.
  ASC pins no JAM version of its own.

## Verified

- Three-OS CI on every merged change: typecheck, build, full tests, release checks,
  packaging, packaged smoke.
- Linked worktree continuity walked on a real project: a worktree created and never
  registered resolved to its workspace and registered its locator; an independent clone
  of an already-registered remote resolved to nothing and was not registered.
- A host session hook run in that unregistered worktree, with no prior ASC command,
  restored the workspace's real state.
- Code and work channels observed together in one pass on a real project, and a repeated
  pass over unchanged external state produced no new reports — across a process restart.
- macOS registration observed end to end: registered, loaded by the OS, a pass run and
  exited cleanly, with no user action.
- Host hook coexistence checked against a copy of a real host configuration: existing
  hooks preserved, three reinstalls produced no duplicates, uninstall left the others.

## Known limitations

- **Windows and Linux registration are not exercised.** Both adapters are fixed by
  contract tests only. Neither has been run on a live machine, and this release does not
  claim they were.
- **Reboot and login recovery are not exercised.** The macOS registration runs at load,
  which is that path, but no reboot was performed.
- **Credentials under a service-started process are not exercised.** Whether `gh`, `glab`
  and JAM credentials resolve the same way when the OS starts the process, rather than a
  shell, has not been measured.
- **No second host adapter exists.** Host neutrality is fixed structurally — core imports
  no adapter and branches on no host id — but only one host has been driven.
- A workspace whose checkouts are all gone stops being observed and keeps its state. It
  is never cleaned up automatically, so it stays visible in `runtime list` until a person
  removes it.
- The machine registration records the absolute path of the runtime that created it. If
  that installation is removed, the registration must be removed with
  `asc runtime service uninstall`.
