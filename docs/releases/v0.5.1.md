ASC 0.5.1 makes a first install finish on its own. Everything a person had to
repair by hand after the official entry point — adopting a profile, recording an
identity, editing bindings, declaring a canonical source, re-locking — is now
part of the one command, and the machine registration no longer points at a
location that disappears.

## What changed

- **One command reaches READY.** A repository whose remote proves a project
  identity gets its profile created and used, the approver recorded from the
  authenticated provider that can name you, the bindings discovery can prove
  written into the profile, and the canonical source declared from the remote's
  own default branch. Each of those happens only where there is evidence: a
  repository with no shared remote still stops for a person to choose, no
  approver is invented when nothing can name you, and ambiguous bindings are
  left alone.
- **The registration points at something that will still be there.** Running the
  entry through `npx` used to record the npx cache as the runtime, so clearing
  that cache left a registration calling a path that no longer existed. A
  temporary location is now never recorded; the globally installed runtime is
  preferred, and the Node it records must exist, be Node 24 or newer, and live
  somewhere stable. When none of that holds the machine is not registered and
  the reason is said out loud.
- **Registration happens last, and only when there is something to watch.** It
  used to be planned before attachment, so the OS began passing over a workspace
  whose identity and bindings were not set yet and a person saw failures before
  finishing setup. A run that stops for a person now registers nothing.
- **A declared work binding answers for work items.** The profile declared one
  and monitoring used it, yet `proceed --work` still reported no channel could
  read work items: with both a code and a work provider offering resource reads,
  nothing said which one answers. The split is a capability shape — a work
  channel lists and reads resources and does not know code changes — not a
  provider name.
- **Work starts inside a logical session.** The guard already standing in front
  of Bash now also stands in front of Edit, Write, MultiEdit and NotebookEdit.
  In an attached workspace, a mutation from a session ASC does not manage is
  refused with the exact commands that enter one. Reading is untouched, and a
  project with no ASC attachment passes as before.
- **An attached workspace with no canonical source is not reported as fully
  open.** A new gate names what is missing instead of leaving a person to
  discover it through verdicts that can never be reached.
- **A failed apply answers with a document.** An effect throwing used to leave
  stdout empty and the exit code alone to explain it.

## Install / Upgrade

```bash
npx --yes @asc-agent/bootstrap@0.5.1 setup apply --json
```

Already installed:

```bash
npm install -g @asc-agent/runtime@0.5.1
```

Existing state is read as it is; nothing is migrated. An existing machine
registration compares as behind the new form and converges with one
`asc runtime service install` — and if it was recorded against an npx cache,
that is the run which fixes it.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.5.1 setup apply --json
```

Its answer is different: where it used to stop and ask which profile, a
repository that proves one is now adopted, attached and wired in the same run.

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change and no migration.
- `setup status` reports a fourth gate, `canonical`.
- The registration file format gains environment and log entries; older
  registrations converge through the existing stale path.
- The host guard covers file-editing tools as well as Bash. Sessions ASC does
  not manage are unaffected in projects with no attachment; in an attached
  workspace an unmanaged mutation is now refused rather than silently allowed.
- JAM is consumed through its published packages at the version JAM reports for
  itself.

## Verified

- Three-OS CI on every merged change: typecheck, build, 1413 tests, release
  checks, packaging, packaged smoke.
- Against a real project in an isolated home: one `setup apply` went from
  nothing to READY with every gate open — profile adopted from the remote,
  approver recorded, both bindings declared, canonical source `origin/develop` —
  with nothing remaining and a second run changing nothing. The repository was
  untouched.
- The canonical source is read from the remote rather than the local
  `origin/HEAD`, which on that checkout still said `main` where the remote says
  `develop`; a session issued afterwards recorded the real commit as its
  baseline.
- `proceed --work` on a live work item returned a state built from both sides at
  once: the tracker reporting the item closed, and the canonical branch's own
  commits confirming the change landed.
- The packaged smoke walks the zero-base path end to end and still stops for a
  person where the repository proves nothing.

## Known limitations

- **Windows and Linux registration are not exercised.** Both adapters are fixed
  by contract tests only; neither has been run on a live machine.
- **Reboot and login recovery are not exercised.**
- **No second host adapter exists.** Host neutrality is structural — core
  imports no adapter and branches on no host id — but only one host has been
  driven.
- **`CREATE_NEW` against a real coordination provider is not exercised**, and
  GitLab remains the only coordination surface.
- The canonical source is declared only when the remote answers what its default
  branch is. Where it cannot be asked, none is written and the gate says so.
- A workspace whose checkouts are all gone stops being observed and keeps its
  state until a person removes it.
