ASC 0.5.4 fixes a state where a project looked attached but the machine never
watched it. It closes the last defect found by installing 0.5.x from nothing on
a real machine.

## What changed

- **A location whose workspace is gone is not registered.** The index holds two
  tables: the workspaces, and the locations that point at them. Where a location
  survived but its workspace did not, attach read the location, answered
  "already registered", and returned. Attachment looked healthy while the
  machine-wide view never listed that workspace again — so the registered
  service passed over every workspace except that one, silently and for good.
  Such a location is now registered again, reusing the same workspace id when
  its state directory is still there, so sessions and evidence do not end up
  orphaned behind a new id. The repair says so rather than happening quietly.

## Install / Upgrade

```bash
npx --yes @asc-agent/bootstrap@0.5.4 setup apply --json
```

Already installed:

```bash
npm install -g @asc-agent/runtime@0.5.4
```

If a project of yours is attached but missing from `asc runtime list`, running
the entry again in that project registers it and the machine begins watching it.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.5.4 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change, no surface change, no migration. An index that is
  already consistent is untouched.

## Verified

- Three-OS CI: typecheck, build, 1418 tests, release checks, packaging,
  packaged smoke.
- Found by re-attaching a real project whose index entry had been removed while
  its location entry remained, and confirmed by the regression over that exact
  shape.

## Known limitations

Unchanged from 0.5.1: Windows and Linux registration, reboot and login recovery,
a second host adapter, and `CREATE_NEW` against a real coordination provider are
all still unexercised, and GitLab remains the only coordination surface.
