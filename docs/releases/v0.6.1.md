ASC 0.6.1 stops an update from halting every project on the machine.

## What changed

- **A runtime version move is not configuration drift.** `profile.lock` exists to
  catch configuration a person changed. Replacing the runtime changes
  `ascCore.version`, the adapter build numbers that ship with it, and the
  `configurationDigest` those two feed — three fields, none of them edited by
  anyone. Until now the guard stopped every command on that alone, and told the
  person to re-lock. The guard now stops only on drift a person is responsible
  for: profile, preset, override or capabilities. A lock written by an older
  build still says so, once, on the way past.

## Why this is here

0.6.0's `asc update` was the first path that replaced the runtime without also
re-running `setup` — and `setup` re-locked as a side effect, which is why nobody
saw this. Measured immediately after updating this machine: all three attached
workspaces were stopped, two of them stuck at `0.3.1 → 0.6.0`, having missed
every background pass for several releases while looking attached and healthy.

## Install / Upgrade

```bash
asc update
```

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.6.1 setup apply --json
```

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.6.1 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change. `profile.lock` is neither rewritten nor migrated — a
  lock written by an older build keeps working and records the version it was
  written by until the next `asc profile resolve --write`.
- `compareLock` still reports version fields; only the guard's verdict changed.

## Verified

- Three-OS CI: typecheck, build, tests, release checks, packaging, packaged smoke.
- Two regressions: a version-only difference does not stop a run and is reported
  as a stale lock; an override edit still stops one even when the version moved
  with it.
- Real machine: the three workspaces that the 0.6.0 update had stopped run again
  without any lock being rewritten.

## Known limitations

Unchanged from 0.6.0: no `--to <version>`, and Windows and Linux updates are
unexercised.
