ASC 0.8.0 separates three things that were tangled: who owns the work, who decides, and
who executes. The commands a person types are now the work itself, not the machinery
under it.

## What changed

- **Execution Mode — `asc mode manual` / `asc mode auto`.** One field in the existing
  policy store answers a single question: who carries out an approved act. MANUAL means
  ASC still tracks work, sessions, progress, review and audit but does not force external
  writes through itself; the guard hard-blocks nothing and leaves an advisory line instead.
  AUTO means an ASC-managed agent runs on its own and outward writes travel the approved
  path. Neither mode approves anything on a person's behalf, and neither changes a
  session's owner, scope or handoff.
- **A workspace nobody chose a mode for is not in AUTO.** AUTO exists only where someone
  turned it on and readiness measured READY, so an absent record enforces nothing — an
  enforcement nobody chose and nothing measured is exactly what this release is against.
  Upgrading a 0.7 workspace therefore relaxes the guard until a person runs `asc mode auto`,
  and `asc status` says which of the two states it is in.
- **AUTO refuses to turn on unless the whole managed path is usable.** `asc mode auto`
  measures nine axes — control-plane, controller, binding, executor, provider, review,
  verify, guard, host — from facts other commands already report, and stays in the current
  mode when any of them is not READY. Being able to run `asc status` is not enough: if the
  target cannot be read before a write, or read back after one, AUTO does not turn on.
  This closes what 0.7.1 measured on a real machine: a raw external write blocked by the
  guard while the safe alternative was blocked by the host's own permission layer, with
  no exit between them. The guard now never blocks an ASC command, host installation adds
  an explicit allow rule for them, and `asc mode manual` is the official exit.
- **Remote Review — read the facts before writing, read them back after.** One judgement
  serves both modes: it answers READY, REVIEW_REQUIRED or NOT_EXECUTABLE from what the
  provider read — target identity, source and remote SHA, divergence, an already-open
  change, missing facts. `asc work publish --review` shows it and changes nothing. It is
  not a second approval: a person's instruction settles who decides, and the review settles
  whether the facts still hold. What was approved is pinned as a commit, not a branch name,
  and the execution path revalidates it immediately before writing. Afterwards the result
  is read back from the provider; a mismatch is reported as NOT_VERIFIED rather than
  success, and a write whose outcome is unknown is UNCERTAIN — never retried blindly.
- **What a project decides stays the project's.** The review compares repository identity,
  never branch policy: a canonical source is what judgement is measured against, not a list
  of the only branches that may be written. A part branch in the bound repository is not a
  binding mismatch.
- **`asc status`.** One screen for what is installed, what is attached, which mode is in
  effect, whether AUTO is available and why not, what work is running, what is waiting for
  a person, and what to do next. It aggregates existing readers; it stores nothing of its
  own, and it does not claim more than the evidence: attached is not healthy, and AUTO is
  not a usable path.
- **`asc work` — start, status, pause, resume, publish, finish, inspect.** The internal
  steps are unchanged and still there; a person no longer types them in order.
  `asc work finish` writes the handoff, releases the physical binding, collects and
  archives in one command. `asc work publish` is the official outward write: proposed
  action, decision authority, grant, executor, read-back, audit — the grant path is not
  bypassed, it is what the command runs.
- **`asc refresh` and `asc uninstall`.** `refresh` keeps the version and re-converges only
  what this runtime installed — never the profile, the workspace, the identity, the
  bindings, the sessions or the mode. `uninstall` removes the registration, the host
  integration and the installed runtime, in that order, and leaves every byte of `~/.asc`
  in place. There is no purge command. It refuses while a session or a physical run is
  still live, naming what would be abandoned; and in AUTO it — like `asc host claude
  uninstall` and `asc runtime use development` — asks for controller authority, because
  each of them takes ASC's enforcement away with it.
- **`asc update` now refreshes through the new build's own `refresh`.** Update and refresh
  no longer each carry their own idea of what a current installation looks like.
- **Default help shows nine namespaces.** `setup · status · update · refresh · uninstall ·
  mode · work · inbox · runtime`. Everything else moved to `asc help --advanced`, where it
  still works. `asc init`, `asc proceed` and `asc progress show` keep working as deprecated
  aliases for two minor releases, naming their replacement — in `--json` output as
  `deprecated` and `replacement` fields.

## Install / Upgrade

```bash
asc update
```

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.8.0 setup apply --json
```

Existing workspaces come up with nothing enforced, because nobody has chosen yet. Choose
explicitly with `asc mode manual` or `asc mode auto` — the second one refuses if the
approved path is not usable here, and says which axis is missing.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.8.0 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change. Execution Mode is one key in the policy scope that already
  holds the freeze policy, and a grant gained an optional `basis` recording the commit and
  baseline an approval stood on. An absent mode record means nothing is enforced, so a
  0.7 workspace relaxes until someone runs `asc mode auto`.
- `gitlab.mr.merge` now uses `PUT`, which is what the GitLab API specifies; the previous
  `POST` could only fail, and it failed after a person had already approved the merge.
- `asc setup` with no subcommand now sets up rather than reporting; the report moved to
  `asc status`, and `asc setup status` still answers.
- Host installation adds `Bash(asc:*)` to `permissions.allow` in `~/.claude/settings.json`
  and records it, so `asc uninstall` removes exactly that rule and nothing else.

## Verified

- Three-OS CI: typecheck, build, tests, release checks, packaging, packaged smoke.
- Guard behaviour is checked by running the generated hook as a real process: MANUAL
  blocks nothing and says so, AUTO blocks raw external writes while reads pass, and ASC
  commands pass in both. A workspace with no mode record enforces nothing.
- AUTO readiness refuses on BLOCKED_BY_HOST and on UNKNOWN, and a failed activation leaves
  the mode untouched.
- The execution path is checked end to end against a port that reads and reads back:
  approved-commit drift and an out-of-binding target both stop with zero writes, a
  read-back mismatch is NOT_VERIFIED, a timeout is UNCERTAIN with the grant left unusable
  and no retry, and a refusal is REJECTED.
- Lowering or removing enforcement is checked to require controller authority while in
  AUTO, and `asc uninstall` is checked to refuse while a session is live.
- `refresh` is checked not to call setup, profile, identity, session or mode paths;
  `uninstall` is checked to have no path that deletes user state.
- The `work` façade is checked to call the existing session, controller and grant paths
  rather than a new model.

## Known limitations

- Published acceptance against the 0.8.0 artefact — including a full
  `work start → work publish → GitLab → read-back` round on a real project — is the
  release gate that runs after publishing, not before it.
- A registered workspace whose runtime cannot be read now passes with a warning rather
  than blocking: the mode lives in that runtime, and enforcing what could not be read is
  enforcing what nobody chose. What broke is still said out loud.
- The guard's advisory in MANUAL does not name the target's identity — deciding whether a
  target belongs to this binding is Remote Review's judgement, and reading the remote is
  not something a per-command hook should do. `asc work publish --review` is where that
  answer comes from.
- Windows and Linux lifecycle commands are exercised in CI, not on a real machine.
