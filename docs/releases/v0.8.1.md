ASC 0.8.1 fixes the Windows persistent runtime. On a real Windows machine, `setup apply`
reported a registration it had not actually made, and 0.8.0's own release note named the
reason: lifecycle commands were exercised in CI, not on a machine.

## What changed

- **A registration is no longer made from a path the machine cannot run.** `setup apply`
  printed `Persistent runtime registered with schtasks.` and then finished with
  `verification_failed`, having written `\"C:\Program` as the command and
  `/dev/null/not-installed` as the entry point. The task existed, ran every five minutes,
  and failed in silence. The damage was not a crash — there was none — it was the false
  assurance: nothing was observing, and the machine said something was. Four separate
  defects stacked to produce it, and fixing any one of them left the rest.
- **The global install is found again on Windows.** `npm` there is `npm.cmd`, and since
  the Node security fix a `.cmd` does not run without a shell, so `execFile('npm', …)`
  failed with ENOENT. The helper that reads command output did not tell that failure apart
  from an empty answer, so `npm prefix -g` returned nothing and a runtime that was
  installed was reported absent. The repository already had the fix for this — a resolver
  that runs npm's entry script with the current node — and one caller was not going
  through it. `npm prefix -g` and both `npm view` calls now do.
- **Absence is no longer spelled as a path.** With the global entry reported missing, what
  remained was the caller's stand-in string `/dev/null/not-installed`. The check that
  rejects disappearing locations matches npx caches and temp directories; a string that
  merely looks like a path matches none of them and therefore read as permanent. It was
  promoted to the chosen entry point and written into the registration. The field is now
  optional, so nothing is passed when there is nothing to point at, and the two cases read
  differently: a temporary location and no location at all are different problems.
- **The command line is quoted once.** Each part was wrapped in an escaped quote by hand
  while `execFile` was already escaping for Windows, so a second layer landed on top,
  Task Scheduler read the backslash as part of the value, and `C:\Program Files\...` was
  cut at the space. The same mistake made every registration look stale the moment it was
  created: the status check had to reshape its own string before comparing and still never
  matched what had been written.
- **`refresh` converges a stale registration instead of walking past it.** The planner
  folds "absent" and "stale" into one action, and the refresh path did not separate them
  again — it reported the machine as unregistered and returned, leaving the actual install
  call unreachable. A machine with a stale registration is now converged; a machine with
  none is still left alone, which is what `refresh` has always promised.

Nothing else moved. No new capability, no command surface change, no state schema change.

## Install / Upgrade

```bash
asc update
```

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.8.1 setup apply --json
```

If a Windows machine already carries a broken registration from 0.8.0, `asc update`
replaces it. A registration that points at a path that no longer exists can also be
removed with `asc runtime service uninstall` first; neither step touches `~/.asc`.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.8.1 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change, no command surface change, no change to `~/.asc` contents.
- macOS and Linux registration paths are untouched. The two defects in the quoting and in
  the refresh branch were Windows-only; the other two were in code all three platforms
  share, and their fix does not change what launchd or systemd receive when a stable entry
  point exists.
- A machine that has no installed runtime to point at now refuses to register and says so,
  where 0.8.0 registered a placeholder and reported success. That is the intended change
  in behaviour.

## Verified

- Three-OS CI on the merged change: typecheck, build, the full suite (1590 passing),
  release checks, packaging, packaged smoke.
- Two tests that had been holding the defects in place were corrected — one expected the
  hand-escaped quote, the other reshaped the command string before comparing — and three
  regression tests were added: the quoting is not escaped by hand, a registration made
  moments ago reads as current, and nothing is registered when there is no entry point to
  name.
- On a real Windows machine (Windows 11, Node 24.18.0), with the fixed build: a run with
  no installable entry registers nothing, says `no installed ASC runtime to point at`, and
  exits non-zero; `runtime service install` writes
  `<Command>"C:\Program Files\nodejs\node.exe"</Command>` with no truncation and no
  literal backslash-quote; `runtime service status` reads CURRENT immediately after
  install; and a deliberately stale command is converged by `refresh`, which reports
  `service: converged with schtasks`.

## Known limitations

- The launchd path was not exercised on a real macOS machine for this release. Two of the
  four defects were in shared code, and the shared code is covered by the suite on all
  three platforms in CI, but a real `runtime service install` on macOS has not been run
  since the change.
- Task Scheduler still cannot see an interval change as stale. The interval is passed to
  `schtasks` as its own flag rather than being part of the command line, so a registration
  made with a different interval compares equal. launchd and systemd carry the interval
  inside the unit and do notice. This is a separate defect and is not fixed here.
- Published acceptance against the 0.8.1 artefact runs after publishing, not before it —
  unchanged from 0.8.0.
