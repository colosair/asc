ASC 0.8.2 finishes what 0.8.1 started on Windows, and makes one long-running piece of
damage visible for the first time. Every external command now goes through one place, and
a session that has finished lets go of the machine it was running on.

## What changed

- **One place decides how an external command runs.** `runExternal` resolves the npm shim
  and sets `windowsHide` in a single function, and every call site goes through it. 0.8.1
  fixed the shim resolution in one caller; the same problem was still live in three JAM
  paths, where `doctor`, `probe` and `heal` each spawned their own way. On Windows they
  answered `UNAVAILABLE — spawn npx ENOENT` for a JAM that was installed and working. They
  now use the same resolution `serve` does. Adding a new execution point without going
  through that function is now the awkward thing to do rather than the easy one.
- **Console windows stop flashing for child processes.** Every `glab`, `npx` and `git`
  call made by the runtime ran without `windowsHide`, so each one opened and closed a
  console window on the user's screen. That is fixed for child processes. It is not fixed
  for the scheduled task itself — see Known limitations.
- **`asc work finish` releases the Run it finished with.** It wrote the handoff, collected
  and archived, but left the physical binding in place, so the next `bind` on that Run was
  refused with `RUNTIME_CONFLICT` while the session holding it was already DONE. The
  release now happens in the same command, which is what it always documented.
- **A finished session that still holds a Run is named in `asc status`.** This is the part
  worth reading twice. The automatic cleanup could never see these: it judges a binding
  stale from its history, and a binding that was never released has no history to judge —
  the check reached `history.at(-1)`, found nothing, and moved on. So they accumulated
  silently. `status` now lists them by id with the command that clears them.
- **A scheduled task whose interval no longer matches is stale.** `status` compares the
  registration through `/Query /XML` rather than the localised list output, and compares
  the interval as well as the command. Task Scheduler normalises what it is given —
  `/MO 60` comes back as `PT1H` — so both sides are parsed to minutes before comparing,
  otherwise a correct registration reads as drifted.

## Install / Upgrade

```bash
asc update
```

This works from 0.8.1 on every platform, including Windows — the registry lookup that
failed in 0.8.0 was fixed in 0.8.1.

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.8.2 setup apply --json
```

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.8.2 setup apply --json
```

## What this release does not clean up

**Upgrading may make `asc status` say something it never said before.** If a machine has
bindings left behind by sessions that finished under an earlier version, they are still
there, and `status` now names them:

```text
Degraded:
  - 6 finished session(s) still hold a Run — S-…-01, S-…-02, S-…-03, …
    (asc host claude release <S-ID> --physical <run>)
```

That is not a new problem and this release did not cause it. Those bindings were already
holding those Runs; nothing reported it. This release stops adding to the pile and starts
showing what is in it. **It does not remove anything** — deciding that a session is over
and quietly discarding its record is the kind of silent cleanup that produced the original
defect, so the command is left to a person.

Clearing them is one command per session, listed in the `status` line itself. A machine
with such a pile also cannot run `asc uninstall` until it is cleared, because the gate that
refuses to abandon live work cannot tell abandoned work from live work.

For scale: the machine this release was built on carried six of them, from sessions that
ended a week earlier. None of them appeared in any screen until an uninstall was planned.

## Compatibility

- Node 24 or newer, unchanged.
- No state schema change, no command surface change. `~/.asc` is untouched by this
  release, including the bindings described above.
- `asc status` can now report a degraded line that earlier versions did not report. The
  underlying state is the same; only the reporting changed.
- macOS and Linux registration paths are unchanged in intent, but `runExternal` is code all
  three platforms share — see Known limitations.

## Verified

- Three-OS CI on the merged changes: typecheck, build, the full suite, release checks,
  packaging, packaged smoke.
- The JAM path was compared build against build on a real Windows machine: the published
  0.8.1 answers `UNAVAILABLE — spawn npx ENOENT`, the fixed build answers `AVAILABLE`.
- The interval comparison was measured against a real Task Scheduler: a 60-minute
  registration reads STALE against a 5-minute expectation and CURRENT against a 60-minute
  one, with the `PT1H` normalisation handled.
- The status line for held Runs was reproduced independently by a second session on the
  same machine — published 0.8.1 shows only `no persistent registration`, the fixed build
  additionally lists six finished sessions by id.
- `work finish` releasing its binding is covered by an integration test that spawns the
  CLI against a temporary workspace, rather than by mutating a live machine.

## Known limitations

- **The scheduled task itself still opens a console window each time it runs.** Child
  processes are fixed; the task is not. Two approaches were measured and rejected on a real
  machine: `/RU <user> /NP` requires administrator rights and so cannot be used from a
  normal user install, and Task Scheduler's `Hidden` flag hides the task from the UI list
  and has nothing to do with the execution window. A wrapper that launches without a
  console is the remaining route; it adds a file to `ASC_HOME` and that is a design
  decision this release does not make.
- **macOS and Linux `runtime service install` have not been exercised on a real machine —
  for the second release running.** `runExternal` is shared by all three platforms and CI
  covers it by unit suite on all three, but neither launchd nor systemd has had a real
  registration since these changes. This limitation was stated in 0.8.1 and is repeated
  here rather than quietly carried forward.
- **A development build cannot be told apart from the published one on screen.** Running
  `dist/cli/asc.js` from a checkout reports the same `--version` as the published package,
  and `asc runtime status` — the command whose help says it answers *which build this
  machine actually runs* — reports `target.kind: "package"` for both, because it reads the
  recorded selection rather than the running executable. A build newer than the installed
  integration will therefore say `INSTALLED_STALE` and offer `Next: asc refresh`, and
  following that advice installs unpublished code into the host integration. Anyone
  diagnosing with a local build should be aware there is no on-screen way to confirm which
  one is answering.
- Published acceptance against the 0.8.2 artefact runs after publishing, not before it —
  unchanged from previous releases.
