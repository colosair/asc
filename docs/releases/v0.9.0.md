ASC 0.9.0 removes the hook that stood in front of the shell and pretended to be a
boundary. On a real workspace in AUTO, an agent finished its implementation, typed
`git push`, and was stopped by the PreToolUse guard with three commands to try next. None
of them led anywhere: `asc work start` did not bind the Run, `asc host claude bind` wanted
a session that did not exist, and `asc work publish` had no path out because the
self-hosted GitLab binding was being asked about on gitlab.com. A `glab api` GET for a
package listing was stopped by the same pattern, and binding the Run would not have let it
through.

The audit that followed found that the guard read a RuntimeBinding file and nothing else
— not the logical session, not the grant, not the boundary — and that the one rule it
added which no other layer held was "an AUTO agent must not type `git push` with exact
spelling in one Bash line". Everything else it claimed was either a message, dead code
(the Edit/Write gate was never registered; the installer reused one marker for two
entries), or a copy of a judgement the Executor already makes. Meanwhile the thing that
was actually missing — the healthy path from starting work to owning the Run to publishing
through the managed executor — had three breaks in it.

So this release takes the guard out, fixes the path it was pointing at, and states what
ASC actually guarantees.

## What changed

**The external-write guard is retired.** No PreToolUse hook is installed. The command
classifier, the shell segmenter, the FORBIDDEN patterns, the Edit/Write gate, the
heartbeat it wrote, the capability probe whose `external_write_guard` answer gated
autonomous workers, the worker-settings deny file and the worker contract text are gone.
`asc host claude guard|probe|contract` are gone with them. The SessionStart hook that
restores a session's front stays; it was never part of the guard.

**Upgrading removes the old guard from your host.** `asc update` — and `asc refresh`, and
`asc host claude install` — now also retire what a previous release installed and this one
does not ship: the `guard-hook.mjs` file when its digest still proves ASC wrote it, and
the `settings.json` PreToolUse entries that carry ASC's marker or point at ASC's old
script. A file you edited after install is left where it is and reported; `--force`
removes it. User hooks are not read, not moved, not removed. `asc uninstall` applies the
same ownership rule, and no longer deletes a file it just promised to keep. An untouched
0.8.x host reads as `INSTALLED_STALE` until one of those commands runs.

**Execution Mode means one thing.** MANUAL: a person performs an approved external act at
the shell. AUTO: ASC's managed executor performs it on behalf of an autonomous agent, and
refuses anything it cannot read back afterwards. Neither mode decides what a person must
decide; neither mode sandboxes the shell. `asc mode auto` asks two questions — does a
managed write path assemble here, and can ASC's own commands run in this host without a
permission prompt (an unattended Run cannot answer one). The per-Run scope from 0.8.4 is
unchanged. The `guard` readiness axis and the dead-end action listing are gone.

**`asc work start` binds this Run.** After the session moves to STARTED, RESUMED or
CONTINUE_ACTIVE, the CLI takes the Run id the host reports and claims the RuntimeBinding
through the same code `asc host claude bind` uses. The result is reported next to the
transition, not folded into it: `CLAIMED`, `ALREADY` (no second execution evidence),
`NO_RUN` (not inside a Claude Code Run — nothing written, exit 0), or `CONFLICT`. A
conflict is not success: the session stays STARTED, the holder is named, nothing is
taken over, and the command exits 1 pointing at `asc host claude bind --force` as the
explicit recovery. `asc status` says which sessions this Run holds.

**`--physical` defaults to this Run where ownership is consumed.** `asc work finish`,
`asc session pause|done`, `asc progress report` and `asc host claude release` resolve the
Run id from the host when the flag is absent; an explicit value always wins; outside a
Run the value stays empty and the command says so. `work finish` therefore releases the
binding on the healthy path, which it did not before unless the id was typed by hand.

**The managed executor honours a remote freeze.** `remote.write → DEFER` existed as a
verdict that nothing on the execution path read. The Executor now asks before CLAIM and
answers `FROZEN` without claiming the grant; `asc grant run` records the deferral so
`asc thaw` shows what was held back. The same grant runs once the freeze is lifted — there
is no automatic replay.

**Self-hosted GitLab is addressed on the instance it was discovered on.** Three places
fell back to gitlab.com or to `origin`: the plan cache kept the plan but rebuilt the
adapters, so the discovered endpoint was lost after the first call; `glab auth status` and
`glab api` inferred the host from cwd, which from a hook or the home directory meant
gitlab.com (401, binding read as UNCONFIGURED, `asc work publish` reported no path out);
and the executor pushed to `origin` regardless of which remote the binding was found on.
Adapters now stay with their plan, `glab` is told `--hostname`, discovery records the
remote name, and composition hands it to the executor through a generic `remoteFor`
seam. `ASC_GITLAB_URL` reaches the composed client, not only the probe. Core learns no
host, provider or remote vocabulary.

**The skill describes two mode contracts and does not re-create the guard in prose.** In
AUTO an ASC-managed external mutation goes through `asc work publish`; the agent does not
bypass that path with a raw write for a session ASC is executing. In MANUAL the agent may
perform an external mutation within the stated intent and the project's permissions, and
adds no refusal of its own. Reads — `glab api` GET, `gh … view`, `git fetch` — are never
ASC's to gate in either mode. The skill also stops teaching `asc proceed` (deprecated
since 0.8.3) and the manual bind step.

## Install / Upgrade

```bash
asc update
```

From nothing:

```bash
npx --yes @asc-agent/bootstrap@0.9.0 setup apply --json
```

After upgrading a 0.8.x host, `asc host claude install` (which `update` runs for you)
prints what it retired, and `asc status` shows the host integration as `INSTALLED_CURRENT`.

## Agent setup

The canonical entry is unchanged:

```bash
npx --yes @asc-agent/bootstrap@0.9.0 setup apply --json
```

## Compatibility

- Node 24 or newer, unchanged.
- **Host settings change on upgrade.** The PreToolUse entries ASC owned are removed from
  `~/.claude/settings.json`; the `Bash(asc:*)` allow rule stays. Nothing else in that
  file is touched.
- **`asc host claude guard`, `probe` and `contract` are removed.** `bind` and `release`
  remain as the recovery surface; the healthy path no longer needs them.
- **`asc work start` may exit 1.** When the current Run cannot obtain ownership of the
  session it started, the JSON carries `kind: STARTED` together with
  `binding: { state: "CONFLICT", holder: … }`. Scripts that treated any non-BLOCKED
  outcome as exit 0 should read `binding.state`.
- **`asc status --json` `work[]` entries gain `heldBy`**, and `autoReadiness.axes` has two
  entries instead of three. `deadEnd` is gone from `status` and `mode` output.
- **`asc grant run` can return `FROZEN`.** Exit 1, grant left READY, deferral recorded.
- **State schema is unchanged.** No session, grant, binding or policy record is rewritten.
  Heartbeat files, `worker-settings.json` and `capabilities.json` left under
  `adapters/claude-code/` by 0.8.x are orphaned and harmless.
- **The `GitLabAdapter` `listRemotes` dependency now returns `{ name, url }` pairs.** Only
  tests injected it.
- **The `buildRuntimePorts` `findToken` hook receives the binding as a second argument.**
  Existing single-argument stubs still type-check.

## Verified

- Three-OS CI: typecheck, build, the full suite (1675 tests, 1674 pass / 0 fail / 1
  skipped), release checks, packaging, packaged smoke including the 0.8.x → 0.9.0 upgrade
  plan.
- **Upgrade fixture.** A `~/.claude` shaped like a 0.8.5 install — guard file, manifest
  digests, a marked PreToolUse entry, an unmarked entry pointing at the old script, a user
  hook beside them, a user SessionStart hook beside ours — converges on one `install()`:
  guard file and manifest entry gone, only the user hook left under PreToolUse, both
  SessionStart hooks intact, permissions unchanged, second install a no-op. The
  user-edited variant keeps the file and says why. `uninstall` on the untouched fixture
  removes the same set and nothing else.
- **Binding path.** CLI-level fixtures for CLAIMED, ALREADY, both CONFLICT shapes (exit 1,
  session still ACTIVE, holder unchanged, no execution evidence), NO_RUN, finish without
  `--physical`, progress report without `--physical` inside a Run and refused outside
  one, explicit `--physical` winning over the observed id, and `status` naming the holder.
- **Executor.** Frozen → `FROZEN`, grant READY, zero external calls; thawed → the same
  grant executes once.
- **GitLab.** Discovery records host and remote name; probe asks `glab auth status
  --hostname <host>`; `GlabApiClient` passes `--hostname`; the composed `GitLabScm`
  pushes to the discovered remote whether it is `origin` or `upstream`, independent of
  canonical source order; `ASC_GITLAB_URL` reaches `endpointFor`.
- **Skill.** The AUTO and MANUAL paragraphs are checked against each other: AUTO names
  the managed path, MANUAL says the shell is not intercepted and forbids a self-made
  refusal, and neither paragraph makes an absolute claim across both modes.
- Published acceptance on a real self-hosted workspace is recorded in
  `docs/release/v0.9.0-checklist.md` after publishing, as the release procedure requires.

## Known limitations

**The shell is not a boundary ASC holds, and now nothing pretends it is.** A raw `git
push` typed in AUTO goes out. The record shows the session contract was bypassed — the
managed path leaves evidence and the raw path leaves none — but ASC does not stop it and
does not claim to. This is a statement of the 0.8.x reality as much as of 0.9.0; the
guard matched exact spellings in one Bash line and nothing else.

**A remote freeze no longer stops shell reads.** `asc freeze --deny-remote-read` still
stops ASC's own monitor from polling and the managed executor from writing; a `git fetch`
typed at the shell is outside that.

**`renderProgress` still accepts a `liveness` input that nothing produces.** The heartbeat
that fed it is gone. The field is provider-neutral and tested, so it stays until a later
cleanup.

**`policy.evaluate()` has no production caller**, as it did not before this release. The
write-boundary judgement lives at issue time (`SessionRuntime.issue`) and at execution
time in the remote review's resource check; a file-path check at edit time does not exist
and did not exist when the guard was installed either.

**`OperatorDeps.guard` is the bootstrap/profile.lock check, not the retired guard.** The
name collides; the code does not. Renaming it is churn across four test files and is
deferred.

**Resource identity is path-only.** `group/project` on two different hosts would not be
told apart by the pre-execution review's `BINDING_MISMATCH`; the host is chosen at
discovery and carried by the adapter, not by the identity string.

**macOS and Linux real-machine acceptance remains a single machine.** The published
acceptance for this release runs on the maintainer's macOS host against a self-hosted
GitLab; Windows is covered by CI only this time.
